⚙️ 三、 团队标准作业程序 (SOP)
为了保证8个人不乱，我们需要制定铁律：
API与数据先行契约 (API-First)：数据组和UI组、Agent组必须在第一天就定好JSON数据的接口格式（比如入参出参长什么样）。接口定好后，前端先用假数据（Mock Data）开发界面，不用等Agent组完全开发完。
Prompt版本控制：Prompt就是代码。对 4.1-mini 和 5.1-mini 所有的提示词修改，必须记录版本和修改原因，并跑一遍基础测试集（Ground-truth corpus），防止“改好了一个问题，又引发了幻觉” 。
降级策略 (Fallback Protocol)：针对“API数据缺失或不一致”的痛点，所有调用API的代码必须写Try-Catch。如果飞猪/高德API挂了或者返回空值，立刻静默切换到 SQLite / AGENTS.md 的静态知识库进行兜底 。
四、规定
📜 一、 团队必须统一的三大核心协议 (Protocols)
1. 接口与数据流转契约 (The API Contract)
永远不要等代码写完再联调。Day 1 必须由你和架构师牵头，锁死以下两个核心契约：
* 前后端握手协议：UI 组和后端之间只认 JSON。明确规定“行前规划”入参必须包含什么（如 departure, destination, pet_type, pet_weight），出参长什么样。只要契约敲定，UI 工程师立刻用 Mock 数据配合 Cursor 等 AI 编程工具拉起前端页面，绝不阻塞。
* 工具调用协议 (MCP-style)：数据组封装的飞猪、高德 API，必须产出符合 OpenAI Function Calling 标准的 JSON Schema，并在 AGENTS.md 中详细备注每个参数的边界值。
2. Prompt 版本控制与隔离协议 (Prompt as Code)
在多模型协作中，最忌讳把 Prompt 直接写死在代码里，这会导致追踪“灾难性遗忘”变得极度困难。
* 集中管理：所有的 System Prompt、Few-shot 示例，必须独立存放为 .yaml 或 .json 配置文件（例如 prompts/v1_pre_trip_4mini.yaml）。
* 修改报备：任何对 Prompt 的修改（哪怕只改了一个标点符号或一句话），提交 Git 时必须使用特定的格式：Prompt: 增强了针对超重金毛的高铁合规性约束 v1.2，并在自动化评估 Pipeline 中跑一遍回归测试。
3. 灾难降级与容错协议 (Graceful Degradation)
* 所有调用外部 API（高德、飞猪、天气）的代码，必须包裹 try-catch 逻辑。
* 设定 3秒超时原则。一旦 API 超时或报错，系统必须静默拦截，并立刻去读本地 SQLite 数据库或 AGENTS.md 中的默认/历史缓存数据返回给前端，宁可展示“基础版行程”，也绝不能让用户在页面上看到代码报错（这在体验测试中是致命扣分项）。

💻 二、 协作环境规范：GitHub Codespaces vs. Google Colab
考虑到团队有数据清洗、Agent 逻辑和全栈 UI 开发的不同需求，建议采用混合开发环境策略，切忌“一刀切”。
场景 A：Google Colab （或者本地完善，再上传Code到Colab-注意要修改一些代码使其适配Colab环境）(适用于数据组、评估组及单点 Prompt 测试)
Colab 非常适合做数据清洗、API 连通性测试和单轮大模型对话验证，无需配置环境即可共享。
* 环境隔离：每个任务建立独立的 Notebook。
* 存储挂载：统一使用 Google Drive 作为临时共享云盘。第一步必须是 from google.colab import drive; drive.mount('/content/drive')，所有处理好的 JSON 和 AGENTS.md 知识库统一下载存放在共享目录中。
* 密钥安全 (绝对红线)：严禁在 Notebook 单元格中明文写出各大 API 的 Key。必须使用 Colab 左侧栏的 Secrets (🔑) 功能配置环境变量（如 DEEPSEEK_API_KEY、GAODE_KEY），通过 userdata.get() 调用。
* 算力分配：合理规划算力资源，测试普通逻辑时使用默认 CPU 即可，不要随意开启高规格 GPU 浪费计算单元，确保资源留给最终的评估跑批。
场景 B：GitHub / Codespaces (适用于架构组、Agent组、前端UI组)
当进入多 Agent 编排和前后端联调阶段，Colab 的文件结构就力不从心了，必须转移到工程化环境。Codespaces 提供了标准化的云端 VS Code 环境。
* 分支管理策略 (Git Flow)：
   * main 分支：神圣不可侵犯，只有在内部里程碑（如 4.23 Agent V2 测试通过）时，由组长或架构师 Review 后才能合并（Merge）。
   * dev 分支：日常联调主分支。
   * feature/xxx 分支：每个人自己的开发分支（例如 feature/ui-streaming, feature/gaode-api）。
* 环境标准化 (.devcontainer)：架构师在代码库根目录配置好 .devcontainer/devcontainer.json 和 requirements.txt。任何人启动 Codespace 或在本地拉取代码后，一键 pip install -r requirements.txt 就能保证全员 Python 版本和依赖库完全一致。
